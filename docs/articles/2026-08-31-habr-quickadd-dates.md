# «Завтра в 18:00» — это когда? Разбираем даты и часовые пояса в Python

![Резиновая уточка расследует баг парсера на границе двух дней](https://getdoday.ru/habr-img/s-09-quickadd-cover.png)

В Doday я сделал быстрое добавление задач: вы пишете обычную фразу, а сервис сам выделяет из неё название, срок, приоритет и метки.

Например:

```
Сдать реферат завтра в 18:00 !!! @школа
```

Из неё программа должна получить:

- название — `Сдать реферат`;
- срок — завтра в 18:00;
- высокий приоритет — его задают три восклицательных знака;
- метку — `школа`.

На первый взгляд это обычный разбор строки. Но парсер вернул другое:

```python
title = "Сдать реферат в 18:00"
due_at = "2026-05-04T23:59:00+00:00"
priority = "p1"
labels = ["школа"]
```

Он оставил `18:00` в названии, а вместо указанного времени поставил конец дня по UTC.

Сначала я добавил распознавание формата `18:00`. Казалось, что проблема решена. Но рядом с полуночью задача всё равно могла попасть не на тот день.

Причина была уже не в регулярном выражении. Сервер и пользователь по-разному понимали слово «завтра», потому что находились в разных часовых поясах.

## Почему сервер и пользователь видели разные даты

Парсер считал дату так:

```python
today = datetime.now(UTC).date()
tomorrow = today + timedelta(days=1)
```

Выглядит нормально. Но если в Москве уже 00:30, в UTC ещё 21:30 предыдущего дня. Для пользователя новое «сегодня» наступило, а для сервера — нет. Значит, и «завтра» у них разное.

Исправление короткое:

```python
timezone = ZoneInfo(timezone_name)
today = now.astimezone(timezone).date()
```

Браузер сам знает IANA-имя зоны:

```javascript
Intl.DateTimeFormat().resolvedOptions().timeZone
```

Например, он отправляет `Europe/Moscow`. Парсер находит локальный день, добавляет 18:00 и только потом переводит готовый момент в UTC:

```python
def at_local(day: date, hour: int, minute: int, timezone_name: str) -> datetime:
    timezone = ZoneInfo(timezone_name)
    local = datetime.combine(day, time(hour, minute), tzinfo=timezone)
    return local.astimezone(UTC)
```

Порядок важен: сначала локальные дата и время, потом UTC. Если сделать наоборот, день легко сдвинуть.

## Тест на настоящую проблему

Я поставил часы рядом с границей дня:

```python
def test_tomorrow_uses_users_timezone() -> None:
    # 3 мая, 21:30 UTC = 4 мая, 00:30 в Москве.
    now = datetime(2026, 5, 3, 21, 30, tzinfo=UTC)

    parsed = parse_quick_add(
        "Сдать реферат завтра в 18:00 !!! @школа",
        now=now,
        timezone_name="Europe/Moscow",
    )

    assert parsed.title == "Сдать реферат"
    assert parsed.due_at == datetime(2026, 5, 5, 15, 0, tzinfo=UTC)
    assert parsed.priority == TaskPriority.P1
    assert parsed.label_names == ["школа"]
```

В Москве уже 4 мая, поэтому завтра — 5 мая. А 18:00 по Москве — это 15:00 UTC.

Такой тест проверяет смысл всей строки. Если отдельно проверять слово `завтра` и отдельно `18:00`, их связь легко пропустить.

## Дата без времени — не timestamp

После этого я посмотрел на фразы `до пятницы` и `в пятницу в 18:00`. Они похожи только на экране.

`Пятница` — день календаря без часового пояса. `Пятница в 18:00` — конкретный момент.

Если проект начинается с нуля, лучше разделить их сразу:

```python
due_date: date | None
due_at: datetime | None
```

В Doday схема уже существовала, поэтому я оставил совместимый вариант: `due_at` и флаг `due_date_only`. Главное — не переводить дату без времени между часовыми поясами как обычную встречу.

## За одним багом нашлись ещё три

Пока я гонял обычные фразы, парсер соврал ещё в трёх местах.

### «Через месяц» — не через 30 дней

31 января плюс 30 дней — это 2 марта. Но под фразой «через месяц» обычно имеют в виду конец февраля.

Теперь парсер двигает календарный месяц. Поэтому 31 января превращается в 28 февраля, а в високосный год — в 29 февраля.

### Повтору нужна первая дата

`Тренировка каждый понедельник` создавала правило `weekly`, но не назначала первый понедельник. После выполнения следующая задача не появлялась.

```python
days_ahead = (weekday - today.weekday()) % 7 or 7
first_due = today + timedelta(days=days_ahead)
```

Теперь сохраняются и правило, и первая дата.

### Запятая не должна попадать в метку

Регулярка `@(\S+)` превращала `@магазин,` в метку `магазин,`. Потом рядом могла появиться вторая метка `магазин` уже без запятой.

```python
label_pattern = r"(?<!\w)@([^\s,.;:!?]+)"
```

Заодно я проверил, что `foo@bar.com` не превращается в метку.

## Что проверить у себя

Если ваш код понимает `сегодня`, `завтра` и `через месяц`, попробуйте:

- несколько минут до и после полуночи;
- разные часовые пояса пользователя и сервера;
- дату отдельно и дату вместе со временем;
- 29, 30 и 31 января;
- переход с декабря на январь;
- повтор без первой даты;
- запятую после метки;
- адрес почты со знаком `@`.

Теперь quick-add проверяют 47 целевых тестов. Но важнее то, что парсер больше не смотрит на глобальные часы. Текущее время и часовой пояс приходят снаружи, поэтому любой странный случай можно повторить обычным тестом.
