![Кот пытается понять, когда наступит «завтра в 18:00»](https://getdoday.ru/habr-img/s-08-quickadd-cover.png)

В Doday задачу можно добавить одной строкой:

```
Сдать реферат завтра в 18:00 !!! @школа
```

Я ожидал получить обычную задачу: название «Сдать реферат», срок на завтра в 18:00, высокий приоритет и метку `школа`.

Парсер ответил иначе:

```python
title = "Сдать реферат в 18:00"
due_at = "2026-05-04T23:59:00+00:00"
priority = "p1"
labels = ["школа"]
```

Время осталось в названии, а срок превратился в конец дня по UTC. На первый взгляд это маленькая ошибка в регулярном выражении. На деле проблема оказалась глубже: сервер и пользователь по-разному понимали слово «завтра».

## Почему UTC здесь не помогает

На сервере всё было просто:

```python
today = datetime.now(UTC).date()
tomorrow = today + timedelta(days=1)
```

Этот код выглядит правильно. Но представьте, что в Москве уже 00:30, а в UTC ещё 21:30 предыдущего дня. Для пользователя «завтра» уже считается от новой даты, а для сервера — от старой.

UTC отлично подходит для хранения конкретного момента времени. Но слово «завтра» — это не момент. Это день в календаре пользователя.

Поэтому сначала нужно узнать локальную дату и только потом разбирать фразу:

```python
timezone = ZoneInfo(timezone_name)
today = now.astimezone(timezone).date()
```

На вебе имя зоны можно получить без ручного выбора:

```javascript
Intl.DateTimeFormat().resolvedOptions().timeZone
```

Браузер отправляет, например, `Europe/Moscow`. Парсер получает эту строку отдельным аргументом и больше не пытается угадать, где находится пользователь.

## Тест, который поймал ошибку

Я зафиксировал время рядом с полуночью. Так тест не зависит от часов компьютера и действительно проверяет границу двух дней:

```python
def test_tomorrow_uses_users_timezone() -> None:
    # 3 мая, 21:30 UTC = 4 мая, 00:30 в Москве.
    now = datetime(2026, 5, 3, 21, 30, tzinfo=UTC)

    parsed = parse_quick_add(
        "Сдать реферат завтра в 18:00 !!! @школа",
        now=now,
        timezone_name="Europe/Moscow",
    )

    assert parsed.title == "Сдать реферат"
    assert parsed.due_at == datetime(2026, 5, 5, 15, 0, tzinfo=UTC)
    assert parsed.priority == TaskPriority.P1
    assert parsed.label_names == ["школа"]
```

Почему в результате `15:00 UTC`? Пользователь имел в виду 18:00 по Москве. В базе хранится тот же момент, только приведённый к UTC.

Само преобразование короткое:

```python
def at_local(day: date, hour: int, minute: int, timezone_name: str) -> datetime:
    timezone = ZoneInfo(timezone_name)
    local = datetime.combine(day, time(hour, minute), tzinfo=timezone)
    return local.astimezone(UTC)
```

Важно делать это в таком порядке: сначала собрать локальные дату и время, затем перевести готовый момент в UTC. Если начать перевод раньше, день легко сдвинется.

## Дата и время — не одно и то же

После этой ошибки я отдельно посмотрел на сроки без часов. Оказалось, что фразы `до пятницы` и `в пятницу в 18:00` нельзя считать одинаковыми данными.

- `пятница` — календарная дата без часового пояса;
- `пятница в 18:00` — конкретный момент в определённой зоне.

В новой базе я бы разделил их сразу:

```python
due_date: date | None
due_at: datetime | None
```

В Doday уже была существующая схема, поэтому я оставил совместимый вариант: `due_at` и отдельный флаг `due_date_only`. Главное правило то же: срок с `due_date_only=True` нельзя бездумно переводить между часовыми поясами как обычный timestamp.

## За одним багом нашлись ещё три

Когда основной тест заработал, я прогнал другие обычные фразы. Нашлось ещё несколько мест, которые раньше выглядели нормально.

### «Через месяц» — не всегда через 30 дней

31 января плюс 30 дней — это 2 марта. Человек под фразой «через месяц» обычно ожидает конец февраля.

Теперь парсер двигает именно календарный месяц и ограничивает номер дня последним днём результата. Для 31 января получится 28 февраля, а в високосный год — 29 февраля.

### Повтору нужна первая дата

Фраза `тренировка каждый понедельник` раньше создавала правило `weekly`, но не назначала первый понедельник. Задача существовала без даты, поэтому после выполнения следующая не появлялась.

Правило повтора и первая дата — две разные вещи. Проверять нужно обе.

### Запятая не должна становиться частью метки

Регулярное выражение `@(\S+)` разбирало `@магазин,` как метку с запятой. Она сохранялась в базе, и потом рядом появлялась вторая метка `магазин` уже без запятой.

Я заменил слишком широкое `\S+` на явный список разделителей:

```python
label_pattern = r"(?<!\w)@([^\s,.;:!?]+)"
```

Заодно оставил тест на электронную почту: `foo@bar.com` не должна превращаться в метку.

## Что в итоге стоит проверить у себя

Если ваш код понимает слова `сегодня`, `завтра` и `через месяц`, проверьте хотя бы эти случаи:

- запрос пришёл за несколько минут до и после полуночи;
- пользователь и сервер находятся в разных часовых поясах;
- дата указана отдельно или вместе со временем;
- месяц начинается с 29, 30 или 31 числа;
- год заканчивается;
- повторяющаяся задача получила первую дату;
- после метки стоит запятая или точка;
- адрес почты не распознался как метка.

Мне больше всего помог не новый набор регулярных выражений, а простой контракт функции: текущее время и часовой пояс приходят снаружи, а парсер ничего не берёт из глобальных часов. Благодаря этому любой странный случай можно воспроизвести одним тестом.
